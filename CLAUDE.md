# Воздушный Шар — свод правил проекта

Хакатон ФСП «Продуктовое программирование», 11–13 сентября 2026. Бонусная crash-игра
для «Столото». Полная постановка задачи: `docs/postanovka.pdf` (положи файл сюда же).

## Команда и границы ответственности

Работаем вдвоём параллельно. Граница — HTTP/WebSocket контракт, описанный в
`docs/api.md`. Никто не трогает чужую папку без согласования.

| Зона | Кто | Технологии |
|---|---|---|
| `backend/` | бэкендер | Java 21, Spring Boot 3, WebSocket/STOMP, H2 |
| `frontend/` | фронтендер | React + Vite + TypeScript |
| `config/` | общее, менять по согласованию | JSON конфиг игры |
| `docs/` | общее, менять по согласованию | контракт API, архитектура, мат. модель |

**Правило:** контракт (`docs/api.md`) и конфиг (`config/game.json`) — это единственные
файлы, которые оба человека читают, но перед изменением договариваются в чате/звонке.
Изменил — сразу сказал напарнику и запушил отдельным коммитом, не смешивая с фичами.

## Git-флоу

- `main` защищён, коммитим только через PR.
- Ветки: `feat/backend-<тема>`, `feat/frontend-<тема>`, `fix/...`.
- Один PR = одна папка (`backend/` либо `frontend/`), кроме случаев правки контракта.
- Коммит-сообщение — что сделано и зачем, без "wip", "fix2".
- Перед PR: `git pull origin main`, разрешить конфликты локально.

## Технологический стек (зафиксировано, не менять без согласования)

- **Backend:** Java 21 + Spring Boot 3 (обязательное требование ТЗ — Java).
  Реальное время — WebSocket (STOMP over SockJS). БД — H2 in-memory (простое
  развёртывание для экспертов, не нужен внешний сервис).
- **Frontend:** React 18 + Vite + TypeScript. Анимация полёта шара — CSS transform/
  requestAnimationFrame, без тяжёлых Canvas-библиотек (ради 60 fps на слабых
  устройствах, как рекомендует ТЗ).
- **Конфигурация игры:** `config/game.json`, hot-reload на бэкенде (Spring
  `@RefreshScope` или файл-вотчер). Админ-панель — если успеваем, поверх того же
  файла.
- **Real-time:** WebSocket STOMP over SockJS, топик на раунд (`/topic/round/{id}`),
  fallback на polling не делаем.
- **Демо-доступ:** один фиксированный гостевой пользователь (`guest`), без логина,
  стартовый баланс задаётся в `config/game.json`. Отдельного auth-слоя нет.

## Игровая механика — обязательный минимум (сценарии 1–5 из ТЗ)

Далее — то, что ДОЛЖНО работать без исключений, порядок реализации именно такой:

1. Экран выбора ставки: 4 фрагмента пазла (без бустера, ×2, ×3, ×4), история игр всех
   пользователей, доступ к правилам игры, переключение красная (12 уровней) / зелёная
   (9 уровней) тема.
2. Игровой цикл crash: сервер генерирует точку краха ДО старта раунда, коэффициент
   растёт в реальном времени по WebSocket, кнопка «Забрать» активна после 1-го уровня.
3. Проигрыш: если не забрал — ставка сгорает, экран проигрыша с очками.
4. Бустер: позиция уровня с бустером генерируется сервером по вероятностям
   (line_N_loot_prob), при пересечении — коэффициент × multiplier_tier_N_value.
5. Управление параметрами без пересборки кода — через `config/game.json` (сценарий 5
   проверяется экспертом буквально: поменять points_per_line → перезапустить раунд →
   увидеть новое начисление).

Дополнительно (после того как 1–5 стабильны): экран выбора темы, живой рейтинг,
турнирная таблица, апсейл-попап, полноценная админ-панель, продвинутая анимация.

**Честность:** вся случайность (crash-точка, позиция бустера) считается ТОЛЬКО на
сервере. Клиент никогда не получает и не может повлиять на эти значения до их
раскрытия. Провалидировать это эксперт может открыв devtools — там не должно быть
преждевременных данных о результате раунда.

## Конфигурируемые параметры (из ТЗ, названия можно менять при своей мат. модели)

```
game_id, game_name, game_type, is_active
alpha, max_multiplier, min_crash_multiplier, multiplier_growth_rate, fps, delta
line_1_loot_prob ... line_9_loot_prob   (зелёная тема, 9 уровней)
line_1_loot_prob ... line_12_loot_prob  (красная тема, 12 уровней)
multiplier_tier_1_value ... multiplier_tier_4_value
points_per_line, points_cashout_bonus, points_xN_bonus
MIN_WIN_AMOUNT, POPUP_TIMEOUT
```

## Нефункциональные требования — не забыть

- Адаптив 320px–1920px, мобильный сценарий не менее важен десктопного.
- Chrome/Safari/Firefox, без экспериментальных API.
- Демо-пользователь с ненулевым балансом бонусов (или сценарий пополнения) — обязателен
  для экспертов.
- README.md в корне: стек, инструкция запуска, демо-доступы.

## Как договариваемся о контракте

Смотри `docs/api.md`. Меняется контракт — правьте вместе (голосом/чатом), не
асинхронно каждый у себя. Frontend может начинать работу против мок-сервера (msw /
json-server) с этим же контрактом, не дожидаясь готового backend.

## Карта документации

- `docs/zadacha-razbor.md` — разбор исходного ТЗ по разделам.
- `docs/api.md` — контракт REST + WebSocket (STOMP), источник правды для обеих сторон.
- `docs/rules.md` — пользовательский текст правил игры, отдаётся через `GET /api/rules`.
- `docs/math-model.md` — обоснование мат. модели (crash point, рост коэффициента,
  бустер, provably-fair) — обязательный пункт документации по ТЗ.
- `config/game.json` — единственный источник игровых параметров, синхронен с
  таблицей параметров в `docs/math-model.md`.
