# Математическая модель crash-раунда

Техническая документация для судей/экспертов — соответствует требованию ТЗ
«обоснование подхода, логика генерации случайных событий и расчёта выигрыша,
параметры модели и влияние настроек на результат». Параметры живут в
`config/game.json`, здесь — их смысл и формулы.

## 1. Точка краха (crash point)

Классическая экспоненциальная модель с house edge, стандарт жанра — легко
объясняется, легко настраивается одним параметром `alpha`, и даёт правильное
распределение (много ранних крахов, редкие "иксы").

```
U = server_rng.uniform(0, 1)          // криптографически стойкий RNG
crash_point = clamp(
  alpha / (1 - U),
  min_crash_multiplier,
  max_multiplier
)
```

- `alpha` (house edge, по умолчанию `0.97`) — чем ниже, тем чаще ранние крахи;
  `1 - alpha` — теоретическое преимущество организатора в долгосрочной серии
  раундов (для бонусной игры без реальных денег это управляет темпом сжигания
  баллов, а не прибылью).
- `min_crash_multiplier` (`1.00`) — минимальный возможный крах, чтобы раунд
  всегда успевал хотя бы стартовать.
- `max_multiplier` (`50.0`) — потолок на случай экстремального `U`, защищает от
  переполнения и от нечитаемых значений на экране.

`U` генерируется на сервере через `SecureRandom` **до** начала полёта и никогда
не передаётся клиенту в явном виде до наступления краха.

## 2. Рост коэффициента во времени

```
multiplier(t) = e ^ (multiplier_growth_rate * t)
```

- `multiplier_growth_rate` (`0.45` в секунду) — скорость роста. Общий вид кривой
  — плавный экспоненциальный рост без скачков, что визуально считывается как
  "честный" полёт (в отличие от линейного роста, который выглядит механически).
- `fps` (`10`) и `delta` (`0.1`) — частота тиков WebSocket-события `tick`
  (раз в `delta` секунд), не влияют на саму математику, только на плавность
  отображения. Клиент интерполирует между тиками для 60 fps на экране.
- Раунд завершается (событие `round.finished`), когда `multiplier(t)` достигает
  `crash_point`, вычисленного в п.1.

## 3. Уровни (levels)

Уровень — это не точка во времени, а порог коэффициента. Массив
`level_thresholds` (длина 9 для зелёной темы, 12 для красной) задаёт, при каком
значении `multiplier(t)` засчитывается переход на очередной уровень. Такая
развязка позволяет менять визуальную "высоту" шара и физику полёта независимо
от игровой механики — и настраивается только правкой одного массива в конфиге.

Пороги растут не линейно, а с ускорением (по факту — геометрической прогрессией
с плюс-минус 15–25% шагом), чтобы соответствовать риск-профилю: ранние уровни
преодолеваются часто и легко, поздние — редко и с большим весом для решения
"забрать или рискнуть".

## 4. Позиция бустера

Если выбранная ставка включает бустер (`boost_tier > 1`), сервер перед стартом
раунда один раз разыгрывает **один** уровень, на котором появится бустер —
взвешенный случайный выбор по вероятностям `line_N_loot_prob` для текущей темы
(сумма вероятностей по всем уровням темы равна 1). Выбор фиксируется в момент
`round/start` вместе с `crash_point` и не меняется.

Если шар (по факту роста `multiplier(t)`) достигает уровня с бустером **раньше**
момента cashout — коэффициент умножается на `multiplier_tier_N_value`
(`N` = выбранный игроком tier: 2, 3 или 4), где сам бустер применяется один раз
за раунд. После cashout любое последующее достижение уровня бустера не
учитывается — визуально шар долетает до него, но эффект уже не применяется.

## 5. Выигрыш и очки

```
win_amount = bet * multiplier_at_cashout        // 0, если cashout не произошёл
points = points_per_line * levels_crossed
       + (points_cashout_bonus, если был cashout)
       + (points_boost_bonus, если сработал бустер)
```

Очки начисляются независимо от исхода раунда (в т.ч. при проигрыше — за уже
пройденные к моменту краха уровни), бонусные баллы — только при успешном
cashout.

## 6. Честность (provably fair, упрощённая схема)

1. Перед стартом раунда сервер генерирует `server_seed` (случайная строка) и
   вычисляет `crash_point`, позицию бустера на основе этого seed.
2. Клиенту в ответе на `POST /api/round/start` отдаётся
   `resultHash = SHA256(crash_point || boost_level_index || server_seed)` —
   результат уже определён, но скрыт.
3. После завершения раунда (`round.finished` / `GET /api/round/{id}`) сервер
   раскрывает `server_seed`. Любой желающий может пересчитать SHA256 и
   убедиться, что опубликованный до раунда хеш совпадает — то есть сервер не
   мог задним числом подменить исход по факту действий игрока.
4. Полная криптографическая верификация на клиенте (готовый JS-калькулятор
   хеша) в MVP не обязательна — для прототипа достаточно, что хеш публикуется
   и алгоритм задокументирован здесь.

## 7. Влияние параметров конфига — сводная таблица

| Параметр | Где влияет | Эффект при увеличении |
|---|---|---|
| `alpha` | точка краха | реже ранние крахи, "щедрее" игра |
| `max_multiplier` | точка краха | выше потолок редких больших "иксов" |
| `min_crash_multiplier` | точка краха | поднимает нижнюю границу краха |
| `multiplier_growth_rate` | скорость роста коэффициента | быстрее растёт, раунды короче |
| `level_thresholds[]` | привязка уровней к коэффициенту | смещает, где засчитывается уровень |
| `line_N_loot_prob` | позиция бустера | чаще/реже бустер на конкретном уровне N |
| `multiplier_tier_N_value` | сила бустера | сильнее скачок коэффициента при срабатывании |
| `points_per_line` / `points_cashout_bonus` / `points_boost_bonus` | начисление очков | быстрее растёт счёт игрока |

Сценарий проверки 5 из ТЗ опирается именно на последнюю строку: эксперт меняет
`points_per_line` в конфиге, перезапускает раунд и видит новое начисление очков
за уровень без пересборки кода.
