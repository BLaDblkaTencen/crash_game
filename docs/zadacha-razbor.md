# Разбор задачи «Воздушный Шар»

Источник: `Постановка_задачи_Чемпионат_России_2026_Продуктовое_программирование.pdf`
(бонусная crash-игра для «Столото», Чемпионат России по продуктовому
программированию, онлайн-этап ФСП, 11–13 сентября 2026).

## Продуктовая суть

Игрок ставит бонусные баллы, смотрит на растущий коэффициент выигрыша и должен успеть
нажать «Забрать» до того, как воздушный шар лопнет (crash). Момент краха определяет
сервер до старта раунда — игрок не может повлиять на исход, только на момент выхода.
Цель продукта — не монетизация, а вовлечение: чтобы бонусные баллы тратились
(а не копились без дела), а пользователь возвращался в игру снова за счёт
соревновательности и эффекта упущенной выгоды.

## Обязательный минимум (сценарии проверки 1–5 — должны работать без исключений)

### 1. Экран выбора ставки
- 4 фрагмента пазла: без бустера, ×2, ×3, ×4 — у каждого своя цена в баллах.
- Если баланса не хватает на вариант — кнопка неактивна, при попытке клика — тост
  «Не хватает бонусов».
- Кнопка «Начать» активна только после выбора доступного варианта.
- Обязательна история завершённых игр **всех** пользователей прототипа
  (в т.ч. коэффициенты).
- Обязателен отдельный доступ к правилам игры ДО подтверждения ставки — понятно
  объясняющим списание ставки, рост коэффициента, действие бустера, начисление
  очков и наград.
- Переключение красная (12 уровней) / зелёная (9 уровней) тема — сохраняется
  всегда, даже без отдельного стартового экрана выбора темы.

### 2. Полёт шара
- Коэффициент растёт в реальном времени, значения идут с сервера (клиент не
  считает сам — вопрос честности).
- Кнопка «Забрать» видна, но некликабельна до пересечения 1-го уровня.
- При пересечении уровня начисляются игровые очки (`points_per_line`) — отдельно
  от бонусных баллов, визуальный эффект «+X» и звук.
- Стиль коэффициента меняется по уровням (чёрный → жёлтый → жёлтый с подсветкой →
  жёлтый увеличенный).
- Мини-онбординг при первом запуске: подсказка у кнопки «Забрать» 4 секунды.

### 3. Cashout / crash
- Нажал «Забрать»: выигрыш = ставка × зафиксированный коэффициент, показывается
  «Могли бы забрать больше», шар летит дальше визуально до фактического краха,
  но итог уже не меняется.
- Не нажал до краха: ставка сгорает полностью, анимация взрыва/сдувания.
- Экран результата открывается только ПОСЛЕ фактического краха (не в момент
  cashout).

### 4. Бустер
- Появляется, если выбран фрагмент с бустером ×2+, на одном из уровней (позиция —
  случайна, генерируется сервером на основе вероятностей `line_N_loot_prob` для
  выбранной темы).
- Если шар долетел до уровня бустера раньше cashout — коэффициент умножается на
  `multiplier_tier_N_value`, начисляются доп. очки, есть визуальный/звуковой эффект.
- После нажатия «Забрать» бустер больше не действует.

### 5. Управление параметрами без деплоя
- Минимум: JSON/YAML конфиг с hot-reload. Максимум (доп. баллы): полноценная
  админ-веб-панель.
- Обязательные группы настроек: базовые (game_id/name/type/is_active), параметры
  мат. модели (alpha, max_multiplier, min_crash_multiplier, multiplier_growth_rate,
  fps, delta — или свои аналоги), вероятности позиции бустера по темам,
  множители бустеров (tier 1–4), параметры очков (points_per_line,
  points_cashout_bonus, points_xN_bonus).
- Проверка буквально такая: эксперт меняет points_per_line → перезапускает раунд →
  видит новое начисление. Изменение мат. модели объясняется расчётами/сериями
  запусков, а не по одному раунду.

### Сквозные обязательные требования
- Экран результата: выигрыш/проигрыш, коэффициент, очки за раунд (**всегда, даже
  при проигрыше**), дополнительная игровая награда (форма — на усмотрение команды,
  пазл из брифа не обязателен).
- Кнопка «Играть снова» → к выбору ставки с сохранением темы.
- Автопереход через 10 секунд бездействия на экране результата.
- Каждый раунд пополняет общую историю игр.

## Дополнительные модули (доп. баллы, делать после стабилизации 1–5)

Порядок по возрастанию сложности:
1. Отдельный экран выбора темы (анимированное небо, птицы/облака, звуки).
2. Живой рейтинг во время полёта (обновление ≤0.5 сек, анимации при смене позиции).
3. Турнирная таблица (кнопка-кубок, топ-3 закреплены, деперсонализация имён —
   не обязательна в MVP).
4. Апсейл-попап «Закрепи успех» после выигрыша ≥ `MIN_WIN_AMOUNT`, не чаще раза за
   сессию, автозакрытие через `POPUP_TIMEOUT`.
5. Полноценный админ-веб-интерфейс вместо файла конфига.
6. Продвинутая анимация/звук сверх базового.

## Жёсткие технические ограничения

- **Backend обязателен на Java** (второстепенные не-игровые механики можно на чём
  угодно).
- **Вся случайность и расчёт выигрыша — только на сервере.** Клиент только
  отображает готовые значения, не может повлиять на результат. Провалидировать
  через devtools — там не должно быть преждевременных данных о результате раунда.
- Упрощённый provably-fair: сервер до раунда считает результат → отдаёт клиенту
  хеш → после раунда можно сверить. В MVP достаточно показать хеш и описать
  алгоритм в документации.
- Real-time доставка коэффициента (и живого рейтинга, если делаем) — WebSocket
  либо polling с интервалом не более 1 секунды.
- Адаптив 320px–1920px, три браузера (Chrome/Safari/Firefox последних стабильных
  версий), без экспериментальных API без явного обоснования в документации.
- Нужен демо-пользователь с ненулевым балансом (или сценарий его пополнения) —
  эксперт должен пройти все обязательные сценарии **без обращения к команде**.
- Репозиторий — GitVerse (или другой предоставленный), README.md с инструкцией
  запуска, стеком, демо-доступами.
- Документация в репозитории: архитектура и структура данных, мат. модель и
  обоснование, инструкция по параметрам, перечень реализованного и ограничений.
- Презентация ≤7 минут по структуре: проблема и цель → идея/стиль/механики →
  пользовательский путь → демо цикла (cashout/crash) → демо бустеров → доп.
  модули (если есть) → управление параметрами → архитектура → стек и обоснование →
  развитие/масштабирование.

## Важный нюанс

Формулировки «команда может использовать собственную математическую модель» и
«иллюстрации — примеры, не макеты для копирования» — это не украшение текста, а
прямое указание не копировать бриф 1:1. Оцениваются: собственный визуальный стиль,
рабочая механика, и то, насколько внятно объяснена и обоснована выбранная
математика в документации — а не точное совпадение с картинками из брифа.
